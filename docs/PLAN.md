## 3. Assumptions

1. Clearance is the shortest distance between two footprints (edge to edge), not centre to centre. A pair violates the rule when that distance is strictly less than 0.6 m (a 1e-6 m tolerance keeps exactly 0.6 m compliant). Overlapping items are allowed but always violate.
2. Rotation is in 90° steps. Every catalogue footprint is a multiple of 0.5 m, so footprint edges always sit on grid lines and the clearance rule stays exact.
3. The room origin is the north-west corner: x runs east 0–20 m, z runs south 0–12 m. Item positions are footprint centres.
4. Snapping puts footprint edges on 0.5 m grid lines, and items can never leave the room (clamped).
5. Item types are procedural primitives merged per type (one draw call per type), not glTF, so the time goes into the edit model. The glTF optimisation item is done on a Khronos sample model in a separate bench page.
6. Part numbers and prices are illustrative. Prices are in USD (a property of the price list, not of the UI language); number formatting follows the UI language.
7. Vietnamese strings are machine-assisted translations.
8. The draft autosaves to `localStorage` per project id; refresh does not lose work; the toolbar's undoable Clear resets it. `?seed=N` sessions are not saved.
9. Item tags (e.g. `CAB-01`) must be unique, case-insensitive, so the rule message is never ambiguous.
10. Undo history keeps the last 200 edits.
11. Arrow keys move items in room directions (Up = north), not camera-relative.
12. At 500 items the room cannot satisfy 0.6 m clearance (only about 120 small items can), so the stress scene is mostly red by design; it is for frame-rate measurement.
13. The design document describes the full production system for both surfaces; the editor is a working slice of Surface 2.

## 5. Architecture

### 5.1 Module boundaries

```
src/
  domain/      pure TypeScript, no React or three.js: types, catalog, grid/snapping, ops,
               history, rules (clearance), bom, naming, placement search, proposal,
               proposeFix (greedy clearance fix), seed, serialize
  state/       zustand store (single source of truth), actions, memoised selectors,
               persistence (autosave), bootstrap, query client factory
  i18n/        typed dictionaries, i18next engine, translator, Intl formatters, useT()
  ui/          design-system primitives: Button, IconButton, Tooltip, Tabs, Segmented, Switch,
               Section, Field, Kbd, EmptyState, StateMessage, Toaster, LiveRegion,
               ErrorBoundary, icons
  viewport/    React Three Fiber scene: floor, instanced items, overlays, ghosts, picking and
               pointer interaction, camera rig, perf probe/HUD, WebGL fallback
  features/    palette, item-list, properties, rule-check, bom, toolbar (top bar), status-bar,
               shortcuts (keyboard), assistant
  embed/       postMessage protocol (shared with host), bridge, embedded-mode UI
  host/        demo host page (vanilla TS) for embedded mode
  bench/       model optimisation benchmark page; model source and timings, shared with scripts
  test/        shared test setup and helpers, deployment-header test
  (root)       main.tsx, App.tsx, AssistantTab.tsx (lazy Assistant tab), config.ts, platform.ts
scripts/       asset pipeline (fetch, optimise, inspect) and measurement harnesses
docs/          plan, tasks, contracts, architecture, model optimisation report, AI workflow, design document (git-ignored)
```

Rules: `domain` imports nothing from the app. `viewport` and `features` read state only through selectors and change it only through `state/actions`. Derived data (violations, BOM, item index) is computed from the store by memoised selectors and never stored. ESLint enforces the `domain`, three.js, `ui` and store-write boundaries (CONTRACTS §8).

### 5.2 State model

- Committed document: `items` (ordered array of `PlacedItem`), `history` (`past`/`future` transaction stacks), `revision`.
- Selection and UI: `selectedId`, `hoveredId`, `tool` (`select` or `place` with kind, rotation and a sticky flag), `inspectorTab`, `camera` requests, `locale`, `showStats`, `session` (project and user from the host, or the standalone demo), `clipboard` (kind and rotation).
- Transient interaction (never in history): `ghost` (placement preview position), `drag` (live position of the item being dragged), `proposal` (assistant change being previewed).
- Feedback: `announcement` (screen-reader live region), `saveStatus`. Toasts live in Sonner, not in the store.

Every edit to `items` goes through `commit(state, label, ops, selection)` in `domain/history.ts`, which validates all ops atomically, records the inverse ops, and bumps `revision`. The one exception is `replaceLayout`, which loads a project (or a draft saved by another tab) without a transaction and clears the history. Undo applies the inverse ops; redo re-applies the ops. A drag updates only `drag` while the pointer moves and commits a single `update` op on release.

### 5.3 Rendering and interaction

- One `InstancedMesh` per item type with merged, vertex-coloured geometry: the sample layout and generated layouts of 500 and 2,000 items all draw in 10 draw calls (4 for the room, 4 for the item types, 2 for the violation overlays), 13 with a selection, measured from the performance overlay (ARCHITECTURE §6.4). `?instancing=off` renders one mesh per item for the comparison (506 draw calls at 500 items).
- Per-instance colour for selection and violation tint, plus floor outlines, a 0.6 m clearance halo around the selected item and the placement preview, and red connector lines between violating pairs (all outlines in one draw call, all connectors in one).
- `frameloop="demand"` by default so an idle editor draws nothing (battery and integrated GPUs); `?perf=1` or the stats toggle switches to continuous rendering and shows the HUD (frame rate, frame time, draw calls, triangles, JS heap, GPU string).
- Picking is ray vs item boxes computed from the domain model (cheap and independent of render geometry). Native pointer listeners handle select, drag with pointer capture, place, hover, and a click-vs-orbit threshold. Pointer logic is a plain module so it can be unit-tested.
- The viewport is lazy-loaded so the panels render before three.js arrives; the Assistant tab (with TanStack Query) and the shortcut list are lazy chunks too. If WebGL 2 is unavailable (common on VDI), a fallback message appears and the list, properties and BOM keep working.

### 5.4 Keyboard and screen readers

Arrows move the selection (or the placement preview) one cell, Shift+arrows two cells, R/Shift+R rotate (the preview while dragging or placing), Delete or Backspace removes, Ctrl/Cmd+Z and Ctrl/Cmd+Shift+Z or Ctrl/Cmd+Y undo/redo, Ctrl/Cmd+C/V copy/paste, Ctrl/Cmd+D duplicates, Enter places (so does Enter on the active palette card), Esc cancels, F focuses the camera, 1–4 pick a palette item, [ and ] select the previous/next item, + or = and − zoom, ? opens the shortcut list. Single-character shortcuts can be switched off in the shortcut dialog (WCAG 2.1.4). Moving without dragging is possible with the X/Z steppers (0.5 m) and arrow keys (WCAG 2.5.7), and the Turn view buttons turn the camera without dragging. The item list is a listbox with arrow navigation; after deleting from the list, the next item is selected, and while placing it leaves the arrow keys and Enter to placement. Actions announce results through a polite live region.

### 5.5 Embedded mode

`host.html` on `http://127.0.0.1:5173` frames the editor on `http://localhost:5173/?embed=1`, so the two are different origins. Versioned message envelope. The editor posts `ready` once, to the parent's origin when the browser reports an allow-listed one and otherwise to each allow-listed origin (only the real parent receives it; never `*`); a host whose listener may attach late sends `init` after the frame loads. The editor accepts `init` (user, project, locale, token, expiry, theme) only from allow-listed origins and only from `window.parent`, checks the token's expiry without keeping the token (the slice makes no API calls), requests a refresh 60 s before expiry (halfway for short tokens), and reports `layout-changed` summaries, `resize`, `navigate` requests and `error`s, including `crashed` when its root error boundary catches. The host owns the language and the theme; the embedded editor shows no language switch. The dev server sends `Content-Security-Policy: frame-ancestors` with the allow-listed origins and `vite preview` with `VITE_HOST_ORIGINS` only; `public/_headers` holds the production headers, and a production build without `VITE_HOST_ORIGINS` allows no host. Storage access inside the cross-site frame is guarded (it can throw when third-party storage is blocked).

### 5.6 Assistant (mock)

Streams a reply chunk by chunk (abortable), recognises a few intents in English and Vietnamese (fix clearance, summarise, count items), and for "fix" proposes moves computed by a greedy nearest-free-spot search (`domain/proposeFix.ts`). Each request is a TanStack Query mutation inside the lazy Assistant tab. The proposal is previewed as ghosts, and its card, with the resulting violation count, appears when the reply ends; accept commits all moves as one transaction; a proposal becomes stale (and cannot be accepted) if a moved item changed since it was made or its target is no longer clear of other items. The panel states clearly that the assistant is simulated.

### 6.1 Verification teams

Every check is done by a team of 2–3 agents that discuss, not by one agent (your instruction). Each team runs in three rounds:

1. **Independent pass**: each agent checks its own slice and records findings with evidence.
2. **Discussion**: each agent receives the other agents' findings and must confirm (reproduced), dispute (with evidence) or extend each one, and add anything the others missed.
3. **Agreement**: the team's findings are merged; a finding stands when at least two agents confirm it or one reproduces it with hard evidence (failing test, screenshot, command output).

## 7. Verification

- `pnpm check` runs the typecheck, lint, the format check, the unit and component tests and the production build with its bundle guard. It does not run the browser tests.
- Domain and state tests: snapping and bounds, rotation round-trip, ops validation and atomicity, tag normalisation, undo/redo per edit type, history limit, clearance boundaries, spatial index vs brute force on random layouts, BOM, naming, free-spot search, proposal staleness and the greedy fix, serialisation of malformed input, storage that throws, another tab's save.
- UI tests (jsdom): list ↔ selection sync, properties edits and validation, keyboard shortcuts and announcements, assistant stream → preview → accept → undo, embed protocol origin/source checks and token refresh. Components are also rendered in Vietnamese in their own tests, and `src/i18n/messages.test.ts` checks the dictionaries. R6's check, rendering the whole app in Vietnamese and finding no English-only dictionary string, runs only in the browser (`e2e/flows/language.spec.ts`, `e2e/a11y/language-and-states.spec.ts`).
- Browser checks are headless `@playwright/test` specs in `e2e/` (`pnpm test:e2e`): they click, drag, type and press keys through every interactive flow (select, drag, place, rotate, delete, undo, language toggle, assistant accept, embedded handshake) in a 1920 × 1080 window.
