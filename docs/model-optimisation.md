# 3D model optimisation report

This report covers the brief's 3D model optimisation plus item: one heavy glTF model of 10 MB or more, optimised with glTF-Transform, with before and after numbers for file size, triangle count, draw calls, load time and frame time, and the draw-call difference that instancing makes for repeated items.

File statistics come from the command-line pipeline and are regenerated by `pnpm assets:inspect` into [model-optimisation.json](model-optimisation.json) and the [Asset statistics](#asset-statistics) section. Browser numbers (load time, frame time, measured draw calls) come from the benchmark page and belong in [Browser measurements](#browser-measurements). MB = 10^6 bytes, MiB = 2^20 bytes.

- **Geometry** carries most of the byte saving: the raw file holds 24.0 MB of vertex and index data (20.0 MB of it float vertex data). Simplification with a normal-aware error limit, quantisation and Meshopt compression bring LOD0's geometry and JSON to 0.39 MB.
- **Textures:** 33 JPEG maps at 2048 px decode to about 738 MB of uncompressed RGBA with mipmaps on the GPU. As KTX2 they stay block-compressed: 16.8 MB at LOD0, 4.0 MB at LOD1 and 1.0 MB at LOD2, and the texture bytes shrink from 18.9 MB of JPEG to 5.2 / 1.4 / 0.4 MB. Colour maps use ETC1S unless a decode check shows that ETC1S shifts their colours; on this model that moves the board's colour map to UASTC at LOD0 and LOD2.
- **Draw calls inside the model** drop from 49 to 15 per copy: the 44 repeated parts (16 pawn bodies, 16 glass pawn tops, 4 rooks, 4 knights and 4 bishops) become 10 GPU-instanced draws.
- **Draw calls across copies** stop growing with the number of copies when the benchmark page instances them: 15 draw calls in the file (28 per frame with the transmission pass) for any number of LOD0 copies, instead of 15 (28) per copy.
- **Renders** from one camera, with the board filling a 1600 × 1000 frame: [raw](images/model-raw.png), [LOD0](images/model-lod0.png), [LOD1](images/model-lod1.png), [LOD2](images/model-lod2.png). Why ABeautifulGame:

1. **Unambiguously heavy:** 42.98 MB, which is 40.99 MiB, four times the threshold in either unit. The previous model, CommercialRefrigerator, is 10.13 MB but only 9.66 MiB.
2. **Dense geometry for simplification and levels of detail:** 1.5 million triangles in 24.0 MB of vertex and index data, of which 20.0 MB is float vertex data (417,028 vertices of 48 bytes). The body of a single 5 cm pawn has 47,232 triangles.
3. **Real textures for KTX2:** 33 JPEG maps at 2048 px (base colour, normal, and occlusion-roughness-metalness per piece), about 738 MB of GPU memory once decoded.
4. **Repeated meshes for instancing inside the model:** 16 pawns (body and glass top), 4 rooks, 4 knights and 4 bishops share 10 meshes, so 44 of the 49 draw calls are repeats. This is the same pattern as identical cabinets in an electrical room.
5. **Licence:** CC BY 4.0, a Khronos showcase asset with a clear attribution chain.

The other candidates are texture-bound (MosquitoInAmber, AntiqueCamera and Corset keep over 95 % of their bytes in textures and draw 1 to 3 meshes, so simplification and instancing have nothing to work on), barely above the threshold without repeated meshes (CarConcept), or below 10 MiB (CommercialRefrigerator). The chess set's downside is that it is unrelated to electrical equipment; its glass pawn tops (transmission and volume) also exposed a three.js limitation, worked around as described below.

Swapping the model stays a one-line change: `src/bench/model.ts` keeps CommercialRefrigerator in `MODELS`. Set `MODEL = MODELS.CommercialRefrigerator`, then run `pnpm assets:fetch`, `pnpm assets:optimize` and `pnpm assets:inspect`; the benchmark page follows `MODEL`. The level-of-detail settings below were tuned on the chess set.

## Pipeline

Commands:

1. `pnpm assets:fetch` downloads the pinned model to `public/models/raw/`, verifies its size and SHA-256, prints source and licence, and unpacks KTX-Software locally (macOS arm64).
2. `pnpm assets:optimize` builds `public/models/a-beautiful-game/lod0.glb`, `lod1.glb` and `lod2.glb` from the raw file and writes the attribution README next to them. It takes about 20 s on an Apple M2 Pro. Repeated runs usually produce byte-identical files, but not always: UASTC rate-distortion optimisation is only fully repeatable with one encoder thread, and glTF-Transform's `toktx` always runs `ktx` with at least two (`--uastc-rdo-m` only turns off the threading inside the optimisation step). Encoding the Knight occlusion-roughness-metalness map 96 times, 12 at a time, with the flags `toktx` uses gave the committed bytes 90 times and a variant 6 bytes larger 6 times; decoded, the two differ only in the 128 px mip level, in 144 of its 49,152 channel values, by at most 17 of 255. With one thread all 96 were identical. The rounded figures in this report do not change, but the exact byte counts in `model-optimisation.json` can.
3. `pnpm assets:inspect` writes `docs/model-optimisation.json` and regenerates the [Asset statistics](#asset-statistics) section of this report.

Each level of detail is built from the raw file with these steps, in this order. `snapDirections`, `simplifyToModelError`, `hoistInstanceScale` and `pruneBatches` are small glTF-Transform transforms in `scripts/pipeline.ts`, and `revertColourShifts` is a function there that wraps the ETC1S encoder; the rest are glTF-Transform's own. The last column describes LOD0.

### How the settings were chosen

The shares of visibly changed pixels quoted here come from the one-off [visual check](#visual-check).

**Simplification error.** The limit is an absolute distance in the model's units: 0.1 %, 0.2 % and 0.4 % of the model's largest side (0.705 m), so 0.71 mm, 1.41 mm and 2.82 mm. LOD0 is meant for views where the whole board fills the screen: at 1080 px that is about 0.65 mm per pixel, so the LOD0 error is about one pixel. Each further level is meant for half the screen size of the previous one, so its error doubles and stays about one pixel on screen. glTF-Transform's built-in `simplify` measures the error relative to each mesh's own size instead, which would let the 0.7 m board deviate 14 times more than a 5 cm pawn; `simplifyToModelError` converts the limit per mesh. Doubling the LOD2 error saves a further 23 % of its triangles but raises the share of visibly changed pixels from 7.5 % to 11.2 % (table below).

**Normals in the error.** The simplifier also weighs how far the vertex normals move (weight 0.2, scaled per mesh like the distance), so normals may bend by roughly the error divided by 0.2: about 0.3°, 0.6° and 1.1°. Without this term the chess set's glossy surfaces show it immediately: the remaining vertices keep their original normals, the interpolated shading drifts, and the board's bevelled frame shows dark reflection bands. At a similar triangle count, position-only simplification changes the colour of 26.8 % of the model's pixels visibly, against 3.6 % with normals in the error.

**Vertex splits and tangents.** The export splits vertices whose normals or tangents differ only by float noise. `weld` cannot merge them, and the simplifier treats every split as a seam it must preserve. Step 6 rounds these attributes to an 8-bit grid (steps of 1/127), comparable to the 8-bit octahedral encoding Meshopt stores them with, so that `weld` can merge the noise-only splits. The rounding must also write −0 as 0, because `weld` compares bytes: the export already holds 27,640 negative zeros in these attributes, and the first version of this step raised that to 224,117. They kept 26,927 numerically identical vertices apart (349,700 instead of 322,773 after `weld`) and stopped simplification at those false seams: LOD2 then had 94,908 triangles, and the same error limit now gives 68,326. The splits that remain on the board are real: 1,332 vertex positions on UV seams, 4,357 on tangent seams, 104 on hard normal edges and 99 with UV steps under 1/512 of the texture. Dropping the tangents instead and letting three.js derive tangent frames from screen-space derivatives would also unblock simplification, but it visibly changes the normal-mapped shading compared with the baked tangents (table below).

**Textures.** ETC1S gives each 4 × 4 block a single base colour, stored at 5 bits per channel and shared through a codebook with similar blocks; the pixels of a block differ only in brightness. That suits most colour maps, but it cannot hold subtle hue changes: the board's teal-green marble came out slate blue with green blotches. ETC1S quality 255 or turning off its rate-distortion optimisation did not help (20.5 % and 20.8 % of model pixels beyond ΔE 5 against 21.0 %, measured during verification). UASTC gives every block its own colours at higher precision, with up to three colour subsets per block, at twice the GPU memory of ETC1S (8 bits per pixel instead of 4). Normal and occlusion-roughness-metalness maps always use UASTC, because ETC1S mixes their independent channels; this is the split glTF-Transform's own `optimize` command uses. Colour maps start as ETC1S, and step 10 decodes each one and counts the texels whose colour moved by more than ΔE 5 (CIE76 colour difference, about twice the smallest difference people notice). The 10 % limit sits between this model's piece maps (at most 7.7 %, at 256 px) and the board map (41.3 % at 1024 px, 20.4 % at 256 px); at 512 px the board map's ETC1S result is 5.6 %, so LOD1 keeps it. Re-encoding the board map costs 217 kB of file and 0.70 MB of GPU memory at LOD0, and 22 kB and 0.04 MB at LOD2. At LOD0's design view the board spans about 1,250 px and each piece at most about 200 px, so 1024 px colour maps match or exceed what the screen shows. The data maps run at half the colour resolution: 1024 px data maps change the result by half a point but cost 8.9 MB of file and 21 MB of GPU memory.

### Glass and instancing

The glass pawn tops use `KHR_materials_volume`, whose thickness is given in the mesh's coordinate space. Quantisation (step 11) moves each mesh's dequantisation scale into the node transform, or into the per-instance `SCALE` attribute for an instanced mesh, and divides the thickness by the same factor (0.22 becomes 19.92 for a scale of 0.011); that is correct per the glTF specification. three.js, however, scales volume thickness by the object's model matrix only and ignores per-instance transforms, so instanced, quantised glass rendered about 90 times too thick and refracted the wrong part of the screen. The earlier version of this pipeline kept the glass out of instancing, at 29 draw calls per copy.

Step 12 fixes it in the file instead. All instances of a batch share the same uniform scale s, so the step multiplies the batch node's scale by s, divides the instance translations by s and drops the per-instance scale. glTF applies the instance transform before the node transform, and S(s) · T(t / s) = T(t) · S(s) for a uniform s, so every instance stays exactly where it was, while three.js now finds the scale in the model matrix. The glass tops are instanced like every other repeated piece, and a copy needs 15 draw calls instead of 29.

The benchmark page builds its own instanced copies from each mesh's world transform, which moves the node scale back into its instance matrices, so it still scales the thickness of glass materials by that transform (`src/bench/copies.ts`). In the same one-off check, a headless run of the benchmark page rendered LOD0 the same with instancing on and off (0.05 % of model pixels differ by more than 8 levels).

## Instancing

The benchmark page draws copies on a square grid in two ways:

- **Instancing on:** one `InstancedMesh` per source mesh, sharing its geometry and material, with one instance matrix per copy (meshes that are already instanced in the file keep all their instances in every copy). Draw calls do not grow with the number of copies.
- **Instancing off:** one cloned scene per copy. Geometry and materials are shared, but every primitive of every copy is its own draw call.

Draw calls per frame follow from the scene structure (calculated, not measured). The first number counts one render pass; the number in brackets adds three.js's transmission pass, which draws every opaque object a second time into a render target whenever a transmissive material (the glass tops) is visible: raw 2 × 33 opaque + 16 glass = 82 per copy, optimised 2 × 13 + 2 = 28.

| Copies | Raw, instancing off | Raw, instancing on | LOD0 to LOD2, instancing off | LOD0 to LOD2, instancing on |

| 1      | 49 (82)             | 49 (82)            | 15 (28)                      | 15 (28)                     |
| 100    | 4,900 (8,200)       | 49 (82)            | 1,500 (2,800)                | 15 (28)                     |
| 1,000  | 49,000 (82,000)     | 49 (82)            | 15,000 (28,000)              | 15 (28)                     |

A headless check of the benchmark page reported the bracketed numbers: 82 for one raw copy, 28 for one LOD0 copy, and 2,800 and 28 for 100 LOD0 copies with instancing off and on. Inside one copy, instancing turns the 44 repeated parts into 10 batches, which is the same mechanism the editor uses for identical cabinets.

## Browser measurements

Raw against LOD0, measured in the browser: cold load 1,230.5 against 509.1 ms (median of 5), frame time for 100 instanced copies 105.35 / 106.50 against 13.41 / 14.10 ms (average / 95th percentile), and 82 against 28 draw calls per frame with instancing, at both 100 and 1,000 copies. Summary of the run: [measurements/bench.json](measurements/bench.json).

Benchmark page: `http://localhost:5173/bench.html?model=raw|opt|lod1|lod2&copies=1|100|1000&instancing=on|off`. It runs on its own after loading, shows its progress, and lists every result in a table readable without clicking. "Run again" reloads the page for another cold run.

Protocol:

- **Load time:** cold cache. Each of 5 runs fetches the file with `cache: 'no-store'` and times fetch, Meshopt and KTX2 decoding, scene construction and the first rendered frame, synchronised with a 1-pixel GPU read-back. The median is reported, with all 5 runs listed. Decoders (Meshopt WebAssembly, the Basis transcoder worker) stay initialised between runs, as they would in the editor after the first model, so the first run is usually the slowest.
- **Frame time:** average and 95th percentile of the interval between animation frames over 5 s of continuous rendering, after a 1 s warm-up, timed with `performance.now()`. Each frame ends with a 1-pixel GPU read-back, so frames cannot queue up ahead of the GPU and each interval includes that frame's GPU work. The page also reports the CPU time spent in `renderer.render()`, measured before the read-back, which shows the draw-call cost even when the frame rate is capped by the display.
- **Also recorded:** draw calls and triangles per frame (`renderer.info`), GPU resources, JS heap (Chrome only), GPU string, canvas size, device pixel ratio and browser.
- **Refresh-rate cap and heavy configurations:** a single copy of any variant may render at the display refresh rate, which hides differences in frame time. 100 copies of the raw model draw about 300 million triangles per frame including the transmission pass (calculated), which is enough to show them; 1,000 copies of the raw model would draw about 3 billion and may take seconds per frame.

Method of this run: the production build (`pnpm build`) was served by `vite preview` at http://127.0.0.1:4173 and measured once with `pnpm measure:bench` (`scripts/measure-bench.ts`) in headless Chromium with vsync and the frame-rate limit turned off. The build leaves the git-ignored raw model out of `dist/`, so it was copied into a copy of `dist/` only for measuring. The load time in the table is the harness's cold load, not the page's in-page load described above: 5 runs per variant, each in a new browser context with the HTTP cache disabled, timed from navigation start to the first 1-pixel GPU read-back after the decoded model is drawn (`bench.html` with one copy, instancing on). It therefore includes loading the page, downloading the model from the same machine without network throttling, and decoding it. The contexts share one browser, so compiled shaders can carry over between runs. Frame time uses the page's protocol above; in addition, the harness drains the GPU at the start of every animation frame, so each interval holds one frame's full CPU and GPU time.

## Limitations

- GPU texture memory is an estimate: ETC1S counted at 4 bits per pixel (8 with alpha), UASTC at 8, PNG, JPEG and WebP at 32 (RGBA), plus a third for mipmaps. Actual use depends on the format the device transcodes to.
- Draw calls in the file statistics count one draw per primitive per node for a single copy; renderer passes such as transmission and shadows add to them.
- `hoistInstanceScale` only applies to batches whose instances share one uniform scale, which is what quantisation produces when the source instances are unscaled, as here. A batch with mixed instance scales keeps them, and three.js would render glass in such a batch with the wrong thickness.
- The colour check's 10 % limit was set from this model's maps; a model with noisier colour maps may need a different limit. It measures colour per texel, not on screen.
- The levels of detail still flatten out towards LOD2: the board keeps 9,026 / 8,008 / 6,990 triangles at LOD0 / LOD1 / LOD2 and each rook 6,110 / 3,914 / 2,776, because the simplifier preserves real seams so that textures do not tear and shading stays continuous. meshoptimizer's `Permissive` mode, which may collapse across seams, cuts LOD2 to 52,444 triangles but changes more pixels visibly (see [Visual check](#visual-check)). Going further would need a different representation for far views, such as a baked low-poly board or impostors.
- `simplifyToModelError` measures the model in world space and each mesh in its own coordinates, so it assumes unscaled mesh nodes, which holds for both models in `src/bench/model.ts`. A CAD export in millimetres under a 0.001 root scale would need the node scale folded into the error first.
- LOD0 is designed for the whole model filling the screen. In closer views (a few centimetres from the pieces) its textures and silhouettes are softer than the raw model (10.3 % of model pixels beyond ΔE 5 in the close-up above); a close-up level would keep 2048 px textures and a smaller error.
- The levels of detail are separate files with their own textures, so a renderer can load LOD2 first and fetch LOD0 only for close views. The editor itself uses procedural geometry, so LOD switching is not implemented there.
